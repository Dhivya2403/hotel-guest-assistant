# Sunrise Grand — AI Hotel Guest Assistant

A full-stack guest-facing assistant that answers hotel FAQ questions and checks
room availability for specific dates.

## Setup & Run Instructions

1. Clone the repo and install dependencies:
   ```
   pip install -r requirements.txt
   ```
2. Get a free Gemini API key from https://aistudio.google.com (Get API Key → Create API key).
3. Set it as an environment variable:
   ```
   export GEMINI_API_KEY=your_key_here
   ```
4. Run the app:
   ```
   python app.py
   ```
5. Open `http://localhost:5000` in your browser.

To run the automated tests (no API key required):
```
pip install pytest
pytest test_app.py -v
```

## API Examples (curl)

**Chat endpoint:**
```bash
curl -X POST http://localhost:5000/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "What time is check-in?", "conversation_id": null}'
```

**Availability endpoint (structured, no LLM call):**
```bash
curl -X POST http://localhost:5000/availability \
  -H "Content-Type: application/json" \
  -d '{"check_in": "2026-10-01", "check_out": "2026-10-03", "adults": 2}'
```

**Health check:**
```bash
curl http://localhost:5000/health
```

## Architecture

- **Frontend**: Single HTML page served by Flask (`render_template_string`), vanilla JS, no build step. Chosen for speed and simplicity over React — the app has one screen and no complex client state, so a framework would add build tooling without a real benefit here. A structured date/guest picker sits above the chat for availability requests, separate from free-text FAQ chat, so the guest journey is: ask a general question OR fill in dates for a booking check.
- **Backend**: Flask, two main endpoints:
  - `/chat` — free-text guest questions. Sends the message + conversation history to Gemini, which decides whether to answer directly from the hotel-info system prompt or call the `check_availability` tool.
  - `/availability` — a direct, deterministic endpoint the frontend's date-picker calls, bypassing the LLM entirely for speed and reliability.
- **Data**: `knowledge_base.json` holds hotel info, amenities, policies, and room inventory (including a mock `booked_dates` list per room, standing in for a real booking system).
- **AI/model**: Google Gemini (`gemini-2.5-flash`) via the `google-genai` SDK, using automatic function calling. The API key is read server-side from an environment variable — never sent to or embedded in the frontend.
- **Data flow**: Browser → Flask `/chat` or `/availability` → (for `/chat`) Gemini decides intent → optionally calls `check_availability()` (pure Python, no LLM) → Gemini phrases the final answer → JSON response → rendered in the chat log.

## Which Parts Use AI vs. Deterministic Logic — and Why

- **AI (Gemini)**: Understanding free-text guest questions, deciding intent (FAQ vs. availability), and phrasing natural-language responses. This is inherently variable input, which is what LLMs are for.
- **Deterministic (plain Python)**: Availability calculation, capacity filtering, pricing math, and date validation live entirely outside the LLM in `check_availability()`. This is intentional — an LLM should never be trusted to compute or "remember" whether a room is booked; that's business logic that must be exact and auditable. The LLM only decides *when* to call this function and *how* to phrase the result.

## Preventing Hallucination / Unsupported Answers

- The system prompt explicitly restricts the assistant to the provided hotel info and instructs it to say "I don't know, please contact the hotel" rather than invent details for anything outside that scope.
- Anything involving real numbers (prices, room capacity, availability) is never generated by the LLM — it's computed by `check_availability()` and passed back as tool output, so the LLM is reporting real data, not guessing.

## Failure Handling

- **Gemini API failure/timeout**: caught in `/chat`, logged server-side, and the guest sees a friendly "temporarily unavailable" message (HTTP 500) instead of a raw error or a hang.
- **Invalid input** (empty message, missing dates, bad guest count, malformed dates): validated before any API call, returns HTTP 400 with a specific message.
- **Frontend**: shows a distinct red error bubble for both network failures and backend error responses, and disables the send button while a request is in flight so guests can't double-submit.

## Product & UX Notes

- **Customer problem**: Hotel guests have simple, repetitive questions (check-in time, pool, breakfast, cancellation) that currently require calling the front desk or digging through a website. A chat assistant answers instantly, any time.
- **Guest journey**: A guest lands on the page, can immediately ask a free-text question, or expand the availability picker if they're checking dates for a stay — kept as two separate, clearly labeled paths rather than forcing every query through natural language, since dates/guest counts are more reliably collected via form fields than parsed from free text.
- **Scope cut for time**: No persistent database (in-memory conversation store, resets on server restart), no user accounts/authentication, no real booking/payment flow — this is a guest-facing FAQ + availability *checker*, not a full booking engine, matching the assignment's scenario.
